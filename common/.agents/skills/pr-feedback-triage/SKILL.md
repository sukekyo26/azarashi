# pr-feedback-triage

PR レビュー指摘を「指摘されたから直す」のではなく**技術的根拠**に基づいて判定する。Copilot でも人間でも基準は同じ。判定結果と対応内容は元コメントへ**スレッド返信**として残し、レビュアー側でも追跡できるようにする。

## 大原則

- **権威ではなく根拠で判断する** — 「コードがどう壊れるか／どう改善されるか」を具体的に説明できなければ却下。
- **忖度禁止** — 受諾／却下とも理由を明示する。却下を恐れて不要な変更を入れない。
- **指摘されたスコープを超えない** — 関連する別件のリファクタを混ぜない。
- **指摘の前提そのものを検証する** — 該当コードを読み、指摘が記述する挙動が実際に起きるかを確かめてから判定する。レビュアー（特に Bot）は差分だけを見て周辺の実装を知らないことがある。
- **ラベルで判定を決めない** — ラベルは指摘の性質、判定は根拠の強さ。`STYLE` でもプロジェクト規約違反なら受諾、`BUG` でも前提が誤りなら却下。

## 分類タクソノミー

各指摘に 1 ラベル付ける。判定（受諾／却下）と組み合わせて表記。

| ラベル | 意味 |
|:------|:-----|
| `BUG` | 動作不具合・データ破損・例外漏れ |
| `SEC` | セキュリティリスク（認可漏れ、injection、シークレット露出） |
| `ROBUST` | 防御的検証・エラーハンドリング・契約整合 |
| `DESIGN` | 責務分割・抽象の位置・重複（DRY）・既存共通基盤の再利用 |
| `COMPAT` | 互換性への影響（意図しない破壊、または互換シムの追加要求） |
| `DOC` | コメント／ドキュメントとコードの不一致 |
| `TEST` | テスト欠落・不正確さ |
| `PERF` | 体感できるパフォーマンス問題 |
| `STYLE` | 嗜好・命名・微細リファクタ |
| `YAGNI` | 仮想的将来拡張への過剰設計要求 |

## 判定

| 判定 | 行動 |
|:----:|:-----|
| **A. 受諾** | 修正コミット + 返信 |
| **B. 部分受諾** | 問題意識は正しいが提案が広すぎる／ズレている。必要な部分だけ修正し、受諾範囲と却下範囲を返信 |
| **C. 却下** | 修正せず、却下理由を返信 |
| **D. 保留** | 影響範囲が広い・既存設計の前提に踏み込む。**返信を投稿する前に**ユーザーへ判断を仰ぐ |

傾向として `BUG` / `SEC` / `ROBUST` / `DESIGN` / `DOC` / `TEST` / `PERF` は根拠が具体的なら受諾、`STYLE` / `YAGNI` / 互換シム要求の `COMPAT` は却下に寄る。ただし判定は根拠で決める。

却下しやすい例: 命名・early return vs if-else、削除済み機能の deprecation path、自明な内容のコメント追加、カバレッジ稼ぎだけのテスト、プロジェクトが明示的に選んでいる方針（`CLAUDE.md` 等）と反する提案。

## 実行手順

### 1. 指摘を取得

PR 番号が未指定なら現在のブランチから解決する。

```bash
gh pr view --json number,title,url,headRefName,baseRefName          # PR# 未指定時
gh api --paginate repos/{owner}/{repo}/pulls/<PR#>/reviews          # レビュー本文（サマリ）
gh api --paginate repos/{owner}/{repo}/pulls/<PR#>/comments \
  --jq '.[] | {id, path, line, user: .user.login, bot: (.user.type == "Bot"), in_reply_to: .in_reply_to_id, body}'
```

- inline comment が本体。review summary だけ読んで取りこぼさない。
- `in_reply_to_id` が付くものは既存スレッドへの返信。**スレッドの起点コメント（`in_reply_to_id` が無いもの）を単位**に扱い、同じスレッドに二重返信しない。
- 自分が既に返信済みのスレッドは対象外。差分更新で outdated になった指摘は、現在のコードに対してまだ成立するかを確認してから判定する。

### 2. 各指摘を分類 + 判定

該当コードを読んだうえで、1 件ずつ書き出す。

```
[#1] <ファイル>:<行>  (comment id: <ID>)
  指摘: <レビュアーの指摘内容>
  分類: ROBUST
  判定: A (受諾)
  根拠: <なぜそう判定したか — コードがどう壊れる / 改善されるかを具体的に>
  対応: <何をどう変更するか>
```

### 3. 受諾分のみ修正

- A / B 判定の指摘ごとに、論理的にまとまった単位でコミット分割。
- CHANGELOG 判定: 「エンドユーザーの操作・設定・出力・動作が変わるか？」→ Yes なら `Unreleased` に記載、No なら何もしない（`changelog` スキル参照）。
- push 後に GitHub 側の CI がグリーンになることを確認する。

### 4. PR コメントへ返信を投稿（必須）

判定結果は元コメントへ**スレッド返信**として残す。受諾／却下とも投稿する。

```
判定: <分類> (受諾 | 却下 | 部分受諾)
根拠 / 理由: <なぜそう判定したか>
対応: <何をどう変更したか>   ※受諾 / 部分受諾のみ
コミット: <short SHA>        ※受諾 / 部分受諾のみ
```

部分受諾は `対応` を `受諾範囲:` / `却下範囲:` の 2 行に分ける。

本文は `Write` ツールで一時ファイルに書き出し `-F body=@<path>` で渡す（markdown はバックティック・`$` が頻出し、shell heredoc では引用を誤りやすい）。

```bash
gh api -X POST "repos/{owner}/{repo}/pulls/<PR#>/comments/<COMMENT_ID>/replies" \
  -F body=@/tmp/reply-<id>.md
```

投稿後は一時ファイルを `rm` する。

### 5. ユーザー向けサマリ報告

PR への投稿とは別に、表形式でローカル報告する。

```
| # | ファイル:行 | 分類 | 判定 | 概要 | コミット |
```

末尾に CI ステータス・コミット一覧・返信投稿の有無を併記する。

## チェックリスト

- [ ] 全指摘を取得（review summary + inline comments 両方）、既返信スレッドを除外
- [ ] 各指摘について該当コードを読み、指摘の前提が成立するか確認した
- [ ] 各指摘に〈分類〉と〈A/B/C/D 判定〉と根拠を付与
- [ ] 受諾分のスコープが指摘内容を超えていない
- [ ] CHANGELOG の更新要否を判定
- [ ] コミットを論理単位で分割し、CI がグリーン
- [ ] 各スレッドに返信を投稿（受諾／却下とも、1 スレッド 1 返信）
- [ ] D 判定があればユーザーの判断を得てから返信した
- [ ] ユーザー向け詳細サマリ（表形式）を生成
