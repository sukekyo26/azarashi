# agents instructions

**全ての回答は日本語で行うこと**

## 設計原則

- **シンプルな実装を最優先する** — 読んで即座に意図が伝わるコードを書く。巧妙なテクニックより明快さを選ぶ。
- **DRY 原則** — 同じロジックを 2 箇所以上に書かない。プロジェクトの共通モジュール（ユーティリティ・型・バリデーション）を活用し、なければそこに追加する。
- **後方互換性のために実装を複雑にしない** — 非推奨パスや分岐を積み重ねるくらいなら、破壊的変更 + マイグレーション手順を選ぶ。互換レイヤーは一時的な措置に留める。
- **べき等性を保つ** — セットアップ・生成系の処理は何度実行しても同じ結果になること。既存リソースの再作成・上書きを避け、上書きは明示的なフラグ指定時のみとする。
- **早期失敗と明確なエラー** — 異常は検出した時点で即座に中断する。エラーメッセージにはユーザーが次に何をすべきかを含める。
- **理解してから最小化する** — 変更が触るコードと実際の処理の流れを読み切ってから、最小の解を選ぶ。理解せずに出した小さな差分は、間違った場所に入れば 2 つ目のバグになる。
- **バグは根本原因で直す** — 報告は症状を指す。修正する関数の呼び出し元をすべて grep し、全員が通る共通箇所で 1 回直す。報告された経路だけを塞ぐと兄弟の呼び出し元が壊れたまま残る。
- **必要になるまで作らない（YAGNI）** — 依頼されていない設定項目・抽象化・拡張ポイント・将来用の分岐は書かない（実装が 1 つの interface、製品が 1 つの factory、変わらない値の設定項目など）。ただし信頼境界の入力検証・データ損失を防ぐエラーハンドリング・セキュリティ・アクセシビリティは削減の対象外。
- **省いたものは報告する** — 意図的に作らなかったものがあれば、完了報告に「何を省いたか・どうなったら足すか」を 1 行添える。
- **既存の共通基盤を使う** — 車輪の再発明をしない。自前で書く前に「既存コードベース（ログ・設定・パス解決・バリデーション等）→ 標準ライブラリ → 言語・プラットフォームの組み込み機能 → 導入済みの依存」の順に探し、どれでも足りないときだけ最小限を書く。新しい依存の追加はその後の選択肢で、理由を明示する。
- **同じ規模ならエッジケースに正しい方を選ぶ** — 短く書くことと、脆い手段を選ぶことは別。

## テストとリントのチェック

- **ローカル検証は変更に見合った分だけ** — ドキュメントやコメントだけの変更ならテスト・リントは回さない。コード変更では、変更箇所に関係するテストとリントなど短時間で済むものを選んで回す。全スイートが短時間で終わるプロジェクトなら全部回してよい。
- **全スイートは push 後の CI に任せる** — CI をマージの関門とする。CI の結果はユーザーが確認するので、push 後に CI の完了を待たない（失敗すればマージできず、ユーザーから伝えられる）。
- **CI 失敗は手元で再現してから直す** — 失敗を伝えられたら、失敗したテストを手元で個別に再現し、修正が通ることを確かめてから push する。推測の修正を push して CI で試す往復はしない。
- **自明でないロジックには検査を 1 つ残す** — 分岐・ループ・パーサ・金銭やセキュリティに関わる処理には、壊れたら落ちる最小の検査を既存のテストスイートに足す。自明な 1 行には不要。
- **CI ワークフローを変更した場合** — 参照しているスクリプト・ファイルが実在することを確認する。削除済みのパスが残っていないか grep で点検する。

## コメントの方針

- **デフォルトは書かない** — WHAT が識別子から明らかなら不要。書くのは WHY が非自明（順序依存・呼び出し契約・workaround・bug 履歴）な時だけ、1〜2 行で。
- **意図的な簡略化には限界を書く** — 既知の上限がある簡略化（単一ロック・O(n²) 走査・素朴なヒューリスティック等）には、上限と作り直す条件を `LIMIT:` で始まる 1 行コメントで残す（例: `# LIMIT: 単一ロック。スループットが問題になったらアカウント単位に分ける`）。`grep 'LIMIT:'` で一覧できるようにするため。
- **公開 API の docstring は別物** — 言い換えだけのインラインコメントは避けるが、公開関数・クラスの docstring はプロジェクト規約に従い必要なら書く。
- **避ける** — 「Foo returns the foo」式の言い換え / 「Earlier revisions …」式の墓標 / 手順の逐次解説 / PR description の再述。
- **既存の冗長は引きずらない** — 新規・改修は短く。気付いた既存冗長は別 PR で刈り込む。

## トークン効率と文脈管理

- **ファイルは的を絞って読む** — 全読みする前に `grep` / 検索で当たりを付け、必要な行範囲だけを読む。シンボル定義・該当関数が分かっているなら、その周辺だけ読む。
- **一度読んだものを再読しない** — 既に文脈にあるファイル・出力は読み直さない。編集後の確認のためだけの再読もしない（編集ツールが失敗していれば分かる）。
- **大きなツール出力は本文脈に流さない** — テストログ・ビルド出力・巨大な検索結果などは、丸ごと読むのではなく中間処理（フィルタ・集計・抽出）を通して必要な結論だけを取り込む。
- **rtk の省略出力を「無い」と読まない** — Bash 出力は hook が rtk で畳んでいる（非可逆）。`[+N hidden: rtk recall <hash>]` / `OUTPUT (last N lines)` が付いていたら、ファイルの有無・件数・行番号をその出力から断定せず、`rtk recall <hash>` で取り出してから判断する。
- **出力は簡潔に** — 前置き・要約の繰り返し・自明な手順解説を書かない。結論と根拠を先に、装飾は最小限。
- **倹約のために正確性を犠牲にしない（偽の節約の禁止）** — トークンを惜しんで確認すべきものを読まず推測で進めるのは逆効果（誤った実装・やり直しでかえって高くつく）。削るのは「無駄打ち」であって「必要な確認」ではない。

## ast-grep の利用

- **構造パターンの検索・置換は ast-grep** — 「この形の呼び出しを全部」「この構文を一括で書き換え」は、テキスト検索の正規表現（複数行・ネスト・空白揺れに弱い）やシンボル名検索（形では引けない）ではなく `ast-grep -p '<pattern>' -r '<rewrite>' -l <lang>` を使う。適用前に `-r` 無しで一致箇所を確認する。短縮名 `sg` は非推奨（警告が出る上、Debian の `/usr/bin/sg` と同名）なので使わない。
- **名前が分かっているシンボルはシンボル検索、文字列・設定・非コードはテキスト検索** — ast-grep は同名の別物やスコープを区別しない。定義・参照の追跡は LSP（使えなければ grep）。Markdown・JSON・TOML・ログ文言はテキスト検索のまま。

## CHANGELOG の更新

- **ユーザーから見える変更は CHANGELOG を同時に更新する** — エンドユーザーの操作・設定・出力・動作が変わる変更なら、コミット前に CHANGELOG を更新する。記載の要否・カテゴリ・フォーマット・二言語の同期は `changelog` スキルに従う。
- **CHANGELOG が無いプロジェクトでは更新しない** — リポジトリに CHANGELOG ファイルが存在しない場合は、新規に作成せず CHANGELOG の更新をスキップする。

## ブランチと PR のワークフロー

- **`main` には直接コミット・push しない** — `main` への反映はリリース時の `develop` → `main` PR 経由のみ。`main` への直接 PR も出さない。
- **`develop` にも直接コミット・push しない** — ドキュメント・typo・バージョンバンプなど変更の大小を問わず、必ず専用ブランチ + PR で `develop` に取り込む。
- **専用ブランチの切り方** — 種別ごとに `feature/` `fix/` `refactor/` `chore/` `docs/` `test/` の prefix を付け、最新の `develop` から `<prefix>/<short-kebab-name>` を切る。複数の独立した変更を 1 ブランチに混ぜず、各ブランチは `develop` をベースに PR を出す。
- **粒度の目安**: 1 機能追加・1 バグ修正・1 リファクタリング = 1 ブランチ・1 PR。レビューしやすい粒度を優先する。
- `develop` の取り込み・PR 作成は `sync-upstream` / `pr-create` スキルに従う。

## Git コミットのワークフロー

- **タスク完了時は明示指示なしで `git add` + `git commit` する（自動コミット）** — コミット前に `git status` で変更内容を確認し、`working tree clean` を確認してからタスク完了を宣言する。コミット漏れがないことを検証する。
- **関連する修正単位でコミットする** — 1 つのタスクで複数の変更がある場合、論理的にまとまった単位（機能とそのテスト、設定とドキュメント等）でコミットを分ける。
- **Conventional Commits 形式・英語 1 文** — `feat:` / `fix:` / `docs:` / `chore:` / `refactor:` / `test:` などのプレフィックスを付ける。
- **`.gitignore` 対象のファイルはコミットしない** — `git add` 時に明示的に追加しない。`git status --ignored` で確認できる。

## 作業スコープの規律

- **依頼されたスコープを超えない** — 作業中に発見した別件の修正・リファクタを混ぜない。指摘・依頼されていない箇所のリファクタを織り込まない。
- 別件は別ブランチ・別 PR に切り出すか、ユーザーに報告して判断を仰ぐ。
